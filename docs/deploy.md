# Deploying to Azure

ai-cost-tracker runs in one Azure resource group per environment, defined in Bicep under
[`infra/`](../infra) and deployed by [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml)
on every merge to `main`. Infra changes go through pull requests like code: the workflow's
`validate` job builds and lints the Bicep on every PR that touches `infra/`, and only `main`
deploys, gated by the `production` GitHub environment.

> **Status:** the templates compile and lint cleanly with Bicep 0.48 and the workflow passes
> `action-validator`, but none of this has been deployed to a real subscription yet. Treat the
> first deploy as the test; see [Unverified assumptions](#unverified-assumptions).

## What gets created

| Resource | Default SKU | Purpose |
|---|---|---|
| User-assigned managed identity `<prefix>-id` | | Pulls images (AcrPull), reads Key Vault (Secrets User), and is the identity granted `Reader` on tracked subscriptions. Its principal ID is `ACT_AZURE_PRINCIPAL_ID`; its client ID is `AZURE_CLIENT_ID` so `DefaultAzureCredential` picks it. |
| Log Analytics workspace + Container Apps environment | PerGB2018, 30 days; Consumption profile | Logs for all apps. |
| Container App `<prefix>-api` | 0.5 vCPU / 1 GiB, 1–3 replicas | FastAPI on port 8000, external HTTPS ingress, `/healthz` probes. |
| Container App `<prefix>-worker` | 0.5 vCPU / 1 GiB, exactly 1 replica | `arq ai_cost_tracker.worker.settings.WorkerSettings`, no ingress. One replica so cron jobs run once. |
| Container App `<prefix>-web` | 0.25 vCPU / 0.5 GiB, 1–2 replicas | Next.js on port 3000, external HTTPS ingress. |
| Container Apps job `<prefix>-migrate` | 0.5 vCPU / 1 GiB, manual trigger | Runs `act migrate`; the workflow starts it before rolling the apps. |
| Azure Container Registry | Basic, admin user off | `ai-cost-tracker` (api/worker) and `ai-cost-tracker-web` images, tagged with the commit SHA. |
| PostgreSQL Flexible Server | PG16, Burstable B1ms, 32 GB, 7-day backups | `azure.extensions=TIMESCALEDB`, `shared_preload_libraries` includes `timescaledb`. Database `ai_cost_tracker`. |
| Azure Cache for Redis | Basic C0, TLS only | arq job queue. |
| Key Vault | Standard, RBAC mode, purge protection | Secrets `database-url`, `redis-url`, `postgres-admin-password`. |

Every ACT_* setting in `config.py` is set on the api, worker and migration job (see
`backendEnv` in `infra/modules/apps.bicep`). `ACT_DATABASE_URL` and `ACT_REDIS_URL` are
Container Apps secrets that are Key Vault references resolved with the managed identity.

**Why Azure Cache for Redis and not a Redis container app:** Container Apps only exposes TCP
ingress (which Redis needs) in environments with a custom VNet, and this deployment avoids a
VNet to stay cheap and simple. Basic C0 has no SLA or replica, which is acceptable: a lost
queue only delays work, because the scheduled jobs re-pick every account and ingestion is
idempotent. Microsoft has announced the retirement of Azure Cache for Redis in favour of
**Azure Managed Redis**; when new Basic caches can no longer be created in your subscription,
swap `infra/modules/redis.bicep` for an Azure Managed Redis resource (the app only needs a
`rediss://` URL in the `redis-url` secret).

### How secrets are handled

There are no secrets in the repo, the parameters file or GitHub:

- **Deployer → Azure:** GitHub OIDC with a federated credential on an Entra app registration.
  No client secret.
- **Apps → Azure (ARM, Cost Management, Monitor, Resource Graph):** the managed identity.
- **Postgres password:** generated by the workflow (`openssl rand -hex 32`) only when the
  server does not exist yet or when you ask for a rotation, passed to that one deployment as a
  secure parameter, and written by Bicep into Key Vault together with `database-url`. On every
  other deploy the parameter is empty and both are left untouched.
- **Redis access key:** read by Bicep (`listKeys()`) and written into the `redis-url` secret.

## One-time setup

You need Owner (or Contributor + User Access Administrator) on the target subscription for
these steps, plus rights to create app registrations in Entra. Replace the `<...>` values.

### 1. Resource group and providers

```bash
az login
az account set --subscription <subscription-id>
for ns in Microsoft.App Microsoft.OperationalInsights Microsoft.DBforPostgreSQL \
          Microsoft.Cache Microsoft.KeyVault Microsoft.ContainerRegistry Microsoft.ManagedIdentity; do
  az provider register --namespace "$ns"
done
az group create --name rg-ai-cost-tracker-prod --location westeurope
```

### 2. Deployer identity for GitHub Actions (OIDC, no secret)

```bash
RG_ID=$(az group show -n rg-ai-cost-tracker-prod --query id -o tsv)
APP_ID=$(az ad app create --display-name ai-cost-tracker-deployer --query appId -o tsv)
SP_OID=$(az ad sp create --id "$APP_ID" --query id -o tsv)

# Trust only workflow runs that use the `production` environment of this repo.
az ad app federated-credential create --id "$APP_ID" --parameters '{
  "name": "github-production",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:Prompt-Shields/ai-cost-tracker:environment:production",
  "audiences": ["api://AzureADTokenExchange"]
}'

# Create and update resources in the resource group (and push images to ACR).
az role assignment create --assignee-object-id "$SP_OID" --assignee-principal-type ServicePrincipal \
  --role Contributor --scope "$RG_ID"

# Bicep assigns AcrPull and Key Vault Secrets User to the app identity. Let the deployer
# assign those two roles only, nothing else.
ROLES="7f951dda-4ed3-4680-a7ca-43fe172d538d, 4633458b-17de-408a-b874-0445c86b69e6"
az role assignment create --assignee-object-id "$SP_OID" --assignee-principal-type ServicePrincipal \
  --role "Role Based Access Control Administrator" --scope "$RG_ID" \
  --condition-version 2.0 --condition "(
    (!(ActionMatches{'Microsoft.Authorization/roleAssignments/write'}))
    OR (@Request[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$ROLES})
  ) AND (
    (!(ActionMatches{'Microsoft.Authorization/roleAssignments/delete'}))
    OR (@Resource[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$ROLES})
  )"
```

The deployer never reads Key Vault secret values; it writes them through ARM, which
Contributor allows.

### 3. Sign-in app registration

Follow [entra-setup.md](entra-setup.md). Add the web URL as a SPA redirect URI: the
Container Apps default is `https://<prefix>-web.<environment-domain>/` (printed in the
workflow summary after the first deploy) or your custom domain.

### 4. GitHub environment and variables

Create the environment **production** (Settings → Environments) with required reviewers and
"Deployment branches: `main` only". Add these as **environment variables** (none is a
secret):

| Variable | Example | Notes |
|---|---|---|
| `AZURE_CLIENT_ID` | `$APP_ID` from step 2 | Deployer app registration. |
| `AZURE_TENANT_ID` | `<tenant-id>` | |
| `AZURE_SUBSCRIPTION_ID` | `<subscription-id>` | |
| `AZURE_RESOURCE_GROUP` | `rg-ai-cost-tracker-prod` | |
| `ACT_NAME_PREFIX` | `act` | 2–12 chars, lowercase letters, digits, hyphens. Keep it stable: it names every resource. |
| `ACT_ENTRA_TENANT_ID` | `<tenant-id>` | Sign-in app (entra-setup.md). |
| `ACT_ENTRA_CLIENT_ID` | `<client-id>` | Sign-in app. |
| `ACT_ALLOWED_GROUP_IDS` | `["<group-id>"]` | JSON. Empty/unset = anyone in the tenant. |
| `ACT_ROLE_GROUPS` | `{"owner":["<id>"],"viewer":["<id>"]}` | JSON. |
| `ACT_AZURE_SUBSCRIPTION_IDS` | `[]` | JSON. Empty = every readable subscription with AI resources. |
| `ACT_API_SCOPE` | `api://<client-id>/access_as_user` | Optional; this is the default. |
| `ACT_ALLOWED_IP_RANGES` | `["203.0.113.0/24"]` | Optional ingress allow-list for api and web (e.g. office/VPN egress). Sign-in is required either way. |
| `ACT_PUBLIC_WEB_URL` | `https://costs.promptshields.com` | Optional, once a custom domain is bound. |

Protect `main` so that changes to `infra/` and the workflow need a reviewed PR.

## First deploy

Run **Actions → Deploy → Run workflow** on `main` (or merge a PR). The workflow:

1. Logs in with OIDC.
2. **Bootstrap:** deploys `infra/main.bicep` without the apps and the job, so the registry,
   Key Vault, Postgres and Redis exist. Generates the Postgres password because the server is
   new.
3. Restarts Postgres if `shared_preload_libraries` is pending a restart (it is after the first
   deploy), so TimescaleDB is loaded before migrations.
4. Builds both images and pushes them to ACR tagged with the commit SHA. The web image gets
   the API URL and Entra IDs as build args.
5. Deploys the migration job with the new image (the apps stay on their current image; on the
   first deploy they don't exist yet), runs it and waits for `Succeeded`.
6. Deploys the apps with the new image.
7. Calls `GET /healthz` and writes the web URL, API URL and the managed identity principal ID
   to the job summary.

If step 6 fails on the very first run with a Key Vault or image pull error, the role
assignments had not propagated yet; re-run the workflow.

Then:

- Open the web URL and sign in.
- **Grant the managed identity `Reader`** on each subscription to track. Preferred: an admin
  clicks **Connect Azure** in the app (ARCHITECTURE.md §4.3), which assigns the role or shows
  the command to send to the subscription owner. Manually:

  ```bash
  az role assignment create --role Reader \
    --assignee-object-id <managedIdentityPrincipalId> --assignee-principal-type ServicePrincipal \
    --scope /subscriptions/<subscription-id>
  # or once for many subscriptions:
  #   --scope /providers/Microsoft.Management/managementGroups/<mg-id>
  ```

  The principal ID is in the workflow summary, or:
  `az identity show -g <rg> -n <prefix>-id --query principalId -o tsv`.
- Optional custom domain: `az containerapp hostname add` + `az containerapp hostname bind
  --environment <prefix>-env --validation-method CNAME` on `<prefix>-web`, then set
  `ACT_PUBLIC_WEB_URL` and add the redirect URI to the sign-in app.

## Routine deploys

Every merge to `main` that touches `src/`, `web/`, `infra/`, the Dockerfiles, dependencies or
the workflow runs the same steps. Migrations always run before the apps change image, so new
code never runs against an old schema. Migrations must therefore stay backwards-compatible
with the previous release (expand, then contract in a later release), because the old api
keeps serving while the migration runs.

## Rollback

- **Fast, no rebuild:** point an app back at the last good image, which creates a new
  revision within a minute:
  `az containerapp update -g <rg> -n <prefix>-api --image <acr>.azurecr.io/ai-cost-tracker:<good-sha>`
  (same for `<prefix>-worker`; `ai-cost-tracker-web:<good-sha>` for `<prefix>-web`). The next
  deploy brings them back in line with `main`.
- **Durable:** run the Deploy workflow manually with `image_tag` = the last good commit SHA
  (its images are still in ACR) and tick `skip_migration`. Alembic is not downgraded
  automatically: the older code runs against the newer, backwards-compatible schema. If a
  migration itself must be reverted, write a new forward migration.
- **Infra:** revert the Bicep change in a PR. Deployments are incremental, so resources
  removed from the template are not deleted; delete them by hand if needed.
- **Database:** Flexible Server point-in-time restore (7 days by default) creates a new
  server; point `database-url` at it.

## Rotating the Postgres password

Run the Deploy workflow manually with `rotate_db_password` ticked. It sets a new password on
the server, rewrites `postgres-admin-password` and `database-url` in Key Vault, and restarts
the api and worker revisions so they read the new value. Expect a short blip.

## Cost estimate (default SKUs)

Rough monthly list prices in USD for a small internal deployment in a typical EU/US region.
These are ranges, not quotes: prices vary by region and change over time. Check the
[Azure pricing calculator](https://azure.microsoft.com/pricing/calculator/) before relying on
them.

| Resource | Assumption | Approx. per month |
|---|---|---|
| PostgreSQL Flexible Server | B1ms, 32 GB storage, backups within the free allowance | $15–30 |
| Azure Cache for Redis | Basic C0 | $15–20 |
| Container Apps | api + web at 1 replica, worker 1 replica, mostly idle; consumption pricing with the monthly free grant | $20–70 |
| Container Registry | Basic | ~$5 |
| Log Analytics | 1–5 GB ingested | $5–20 |
| Key Vault | a few thousand operations | < $1 |
| **Total** | | **roughly $60–150** |

Biggest levers: `webMinReplicas = 0` (cold starts on first visit), a smaller worker, shorter
log retention or a log daily cap.

## Security notes and follow-ups

- Postgres and Redis use public endpoints with TLS; Postgres allows Azure-internal traffic
  (the `0.0.0.0` firewall rule), which includes other Azure tenants. Private endpoints with a
  VNet-integrated Container Apps environment are the next hardening step.
- The app connects to Postgres as the server admin. A dedicated least-privilege role, or Entra
  authentication with the managed identity, needs app support for token-based passwords.
- Redis uses its access key; Entra auth for Redis needs token refresh in the arq connection.
- The api and web ingresses are public unless `ACT_ALLOWED_IP_RANGES` is set; every API call
  still needs a valid Entra token from an allowed group.

## Unverified assumptions

Not yet confirmed against a live subscription (tracked in issue #2):

- The Flexible Server RP keeps the existing admin password when `administratorLoginPassword`
  is omitted on update (routine deploys rely on this).
- The TimescaleDB version Azure offers for PG16 supports `create_hypertable(..., by_range(...))`
  as used by migration 0001 (needs TimescaleDB 2.13+). If it doesn't, the migration job
  fails and the apps are not rolled.
- Container Apps resolve the Key Vault references on first deploy without a manual retry
  (role assignment propagation can lag).
- `az containerapp job start` returns the execution name in `.name`, and the execution status
  values used by the wait loop (`Succeeded`, `Failed`, `Stopped`, `Degraded`).
- Container Apps TCP ingress (needed for a Redis container app) requires a custom VNet; this
  is why a managed Redis was chosen.
- Basic C0 Azure Cache for Redis can still be created in the target subscription (see the
  retirement note above).
